# 1.8.1a -- c() promotes all-NA logical to numeric (E14)

## Goal
In `src/vm.rs` `common_concat`, let an all-NA Lgl argument take the target numeric type (Dbl gets NA_real_, Int gets NA_INT) so `c(1, NA, 3)` evaluates, while non-NA TRUE/FALSE mixed with numbers still raises TypeError.

## Notes
- Scope: E14 in EXECUTION_PLAN_1.md (commit a22dad3). Spec §3.2 forbids implicit logical coercion in arithmetic only. §6.1 says `c()` is numeric-promotable.
- `NA` lexes as `LglLit(LGL_NA)` (value 2). `LGL_NA` and `NA_INT` are in `src/value.rs`. `na_real()` and `is_na_real()` are in `src/value.rs`. Import them in vm.rs if not already imported (vm.rs already imports `is_na_real`, `na_real`, `LGL_NA`, `NA_INT`).
- The fix stays in `src/vm.rs`. `promote_dbl` and `materialize_int` in `src/value.rs` are not edited, so `src/value.rs` stays out of scope.
- Empty Lgl args (length 0) set `lgl` but not `lgl_val`, so they never trigger the mixing error and contribute nothing.
- Existing behavior kept: `c(TRUE, 1)` and `c(TRUE, FALSE, 1)` keep erroring. `c(TRUE, NA)` stays Lgl. `c(NA)` stays Lgl.
- Chr with all-NA Lgl (`c("a", NA)`) is not in E14. It keeps the current TypeError. Raise it as a Discovered item if needed; do not fix it here.
- Risk: `lgl` still selects the all-Lgl branch, so `c(NA, NA)` stays Lgl. Dropping `lgl` for all-NA args would make it return Null. Verify `c(NA, NA)` in the test run.
