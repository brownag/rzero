## Notes
- **Value asserts migrated:** 16 value expressions, covering 25 Rust value-assert statements (`assert_val` calls plus the `assert_eq!` / `assert!` lines inside the three `match eval(...)` blocks).
  - `as.numeric` (6 expressions): `c(1.5, 2.5)`, `1:3`, `c(TRUE, FALSE, NA)`, `c(1L, 2L, NA_integer_)`, `c("1.5", "invalid", NA_character_)`, `c()`.
  - `as.integer` (5 expressions): `c(1.1, -2.9)`, `c(TRUE, FALSE, NA)`, `c("123", "invalid", NA_character_)`, `1:3`, `c()`.
  - `as.logical` (5 expressions): `c(0L, 1L, -5L, NA_integer_)`, `c(0.0, 2.5, NA_real_)`, the 8-element string vector (`"TRUE"`, `"T"`, `"true"`, `"FALSE"`, `"F"`, `"false"`, `"foo"`, `NA_character_`), `0:2`, `c()`.
- **Match blocks:** the three `match eval(...)` blocks (len + element asserts on `R0Val::Dbl`) are flattened to one list element per expression, with the value compared by GNU R. The `len` and `is_na_real` checks are implied by the list canonicalization.
- **Error asserts kept in Rust:** 6 (`as.numeric`, `as.integer`, `as.logical` each on `data.frame(a = 1:2)` and `list(a = 1:2)`, all `TypeError:`).
- **Exclusions applied:** none beyond the error asserts. No H4 divergence applies to this function.
- **Risks:** (1) `as.numeric(c("1.5", "invalid", NA_character_))` and `as.integer(c("123", "invalid", ...))` emit "NAs introduced by coercion" warnings on GNU R. The harness compares values, so this should be fine, but confirm on the first run. (2) `as.logical("foo")` and `as.logical("F")` rely on R's string table; the Rust asserts already encode GNU R behaviour. (3) `c()` as an argument to `as.*` must return a zero-length vector in both R0 and GNU R (`numeric(0)`, `integer(0)`, `logical(0)`).
