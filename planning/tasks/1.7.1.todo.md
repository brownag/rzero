# 1.7.1 -- wasm FFI

## Goal
Expose the R0 evaluator to JS through the D6 linear-memory trio (`r0_alloc`, `r0_free`, `r0_eval`) plus `r0_result_ptr`/`r0_result_len`, all added to `src/lib.rs` with zero dependencies.

## Notes
- Analysis (no source edited): `src/lib.rs` has the five `pub mod` lines, `pub use vm::R0Vm; pub use value::R0Val;`, `DEFAULT_FUEL`, and `eval_script(&str) -> Result<R0Val, String>`. `R0Val: Display` (per 1.6.1 notes).
- Signatures confirmed against D6 and the 1.7.1 spec, with no deviations.
- `r0_free` must match `r0_alloc`: both use boxed `[u8]` of exactly `len` bytes, so the layout the free side rebuilds is identical. `Vec::from_raw_parts` is avoided because its capacity must match exactly.
- Clippy: `not_unsafe_ptr_arg_deref` fires on pub non-unsafe fns that deref raw pointer args, so `r0_eval` and `r0_free` are marked `unsafe`. `missing_safety_doc` fires on pub unsafe fns without a `# Safety` section, so each has one.
- `panic = "abort"` is set only under `[profile.release]`. Tests use unwinding, but no `catch_unwind` is added.
- Zero dependencies: only `std` (`thread_local`, `RefCell`, `Box`, `str::from_utf8`).
- Risk: `r0_result_ptr` points into the thread-local Vec. It stays valid only until the next `r0_eval` on the same thread. The JS side must read it before the next call. Document this in the function doc comment.
- Risk: `eval_script` builds a fresh VM per call, so there is no state across `r0_eval` calls. Fine per D6.
- Constraints honored: `lib.rs` only; no JS files; no `static mut`; no `catch_unwind`; zero deps.
